## Example: a host with nested guests

The real shape of a parent machine and its children, as it exists in this repo:

```
machines/
├── .obsidian/                          # the single vault config (SPEC.md §7)
└── hef-proxmox/                        # bare-metal — root node
    ├── STATE.md                        # identity, topology, services, open issues
    ├── CLAUDE.md                       # machine-specific agent rules
    ├── CONTEXT.md                      # Proxmox VE, production hypervisor
    ├── REFERENCES.md
    ├── vault/
    │   ├── 00_INDEX.md
    │   ├── 01_SYSTEM_INFO.md
    │   ├── 02_SERVICES.md
    │   ├── 03_TASK_LOG.md              # 5 most recent entries
    │   ├── 04_NOTES.md
    │   ├── 05_SECURITY.md
    │   ├── 06_BACKUPS.md
    │   ├── 07_UPDATES.md
    │   ├── 08_CONTAINERS.md            # inventory of the guests below
    │   ├── 09_TROUBLESHOOTING.md       # optional
    │   └── archive/2026-Q3.md          # rotated-out task-log entries
    ├── TOOLS/
    ├── VMs/
    │   └── Windows10x64/                    # same layout, recursively
    └── CTs/
        └── LXC/
            ├── hef-net/                # same layout, recursively
            └── hef-docker/             # + 08_CONTAINERS.md — it hosts Docker children
```

The tree is the topology. `STATE.md` carries `parent:`; children are never listed in any
frontmatter field (`SPEC.md §1.2`).

## Scaffolding

```bash
# From the repo root
tools/new_machine.sh my-server --type bare-metal
tools/new_machine.sh my-vm     --type vm     --parent my-server
tools/new_machine.sh my-ct     --type lxc    --parent my-server
tools/new_machine.sh my-ct     --type lxc    --parent my-server --hosts-children
```

Never create the folder structure by hand. Then follow the matching workflow:
[`ADD_MACHINE.md`](workflows/ADD_MACHINE.md), [`ADD_CONTAINER.md`](workflows/ADD_CONTAINER.md)
or [`ADD_NAS.md`](workflows/ADD_NAS.md).

## Naming conventions

- **Machine names:** lowercase, hyphens as separators — `web-prod`, `db-staging`,
  `hef-net`. The folder name and `STATE.md`'s `machine:` value must match.
- **Vault notes:** two-digit numeric prefix, uppercase name — `06_BACKUPS.md`.
  Numbers are **fixed by name, globally** (`SPEC.md §2`), whether or not the file exists
  on a given machine: `08` is always `CONTAINERS`, `09` is always `TROUBLESHOOTING`. A
  number is never reused for a different note, and numbers are never assigned
  positionally as files are added — that is what produced the `06_BACKUPS` /
  `06_CONTAINERS` and `07_UPDATES` / `07_TROUBLESHOOTING` collisions the renumbering
  fixed.
- **Archive files:** `vault/archive/<YYYY>-Q<N>.md`, chosen by the entry's own date.
- **SSH keys:** `~/.ssh/tuneladora_<machine-name>`, generated by
  `tools/setup_tuneladora_control.sh`.

## One vault, and cross-machine links

There is **one Obsidian vault, rooted at `machines/`** — not one per machine. The single
`.obsidian/` config belongs at `machines/.obsidian/`, and per-machine `.obsidian/`
directories are removed (`SPEC.md §7`).

**Cross-machine links are encouraged.** The former rule that each machine's vault was
independent and must not link to another is **revoked**. It forbade linking exactly the
dependencies the notes already described in prose, which is how `STATE.md`'s `depends_on`
and `provides_to` drifted out of step with reality.

Links are **path-qualified, relative to `machines/`**:

```
[[hef-proxmox/CTs/LXC/hef-net/vault/02_SERVICES]]
[[hef-proxmox/CTs/LXC/hef-net/STATE]]
[[hef-nas-4800/vault/06_BACKUPS]]
```

Bare `[[02_SERVICES]]` is ambiguous across eight machines and is not used — including
inside a machine's own vault.
